# Rust の基本設計とコーディング規約

必要な判断に関係する節だけ読む。以下はこのスキルの既定の選び方であり、
Rust言語の必須規則ではない。対象リポジトリの規約と測定済みの要件を優先する。
Edition・MSRV・新構文の選択は [rust-2024.md](rust-2024.md) を参照する。

## Rust と依存を選ぶ

- Rust採用の判断では、メモリ安全性、実行性能、配布形態、必要なライブラリ、チームの保守能力を比較する。既存言語で要件を満たす箇所を、言語の統一だけで書き直さない。ユーザーがRustを指定している依頼では、その前提で実装する。
- 依存追加は標準機能と既存依存で不足する理由から判断する。暗号やプロトコルなどでは、自作の短さより検証された実装を優先する。
- crate候補は必要機能、MSRV、対象OS、ライセンス、保守状況、既知の脆弱性、推移的依存、ビルド負担を確認する。人気やダウンロード数だけで選ばず、更新され得る情報は採用時点で確認する。
- default featuresと実際に有効になるfeaturesを確認する。不要なら無効化するが、別の依存経路から有効化される可能性も見る。公開crateのfeaturesは原則として追加的に設計し、排他的なモード選択を安易に持ち込まない。
- 通常は互換性を考慮したバージョン指定とlockfileの運用を使う。Git依存、完全固定、独自forkは具体的な必要性と更新方法がある場合に選ぶ。crate分割も公開・依存・責務の境界が必要になってから行う。

資料: [Cargoの依存指定](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html)、
[featuresの統合と設計](https://doc.rust-lang.org/cargo/reference/features.html)。

## 所有権とデータ構造を選ぶ

| 必要なこと | 最初に検討する形 | 選び直す条件 |
|---|---|---|
| 呼び出し中だけ読む | `&T`、文字列は`&str`、列は`&[T]`、パスは`&Path` | 所有権の移動や保存が必要なら所有型を受け取る |
| 値を保持する | `T`、`String`、`Vec<T>`、`PathBuf` | ヒープ配置や再帰型には`Box<T>`、実際に所有者を共有するなら`Rc<T>` / `Arc<T>` |
| 順に処理する | `Vec<T>` | キー検索は`HashMap`、キー順の走査・範囲検索は`BTreeMap`、集合操作はsetを検討する |
| 同じ値を共有する | 単一スレッドは`Rc<T>`、スレッド間は`Arc<T>` | 共有可変状態が本当に必要なときだけ内部可変性やロックを加える |
| 借用と所有を使い分ける | 素直な借用型か所有型 | 借用で済む経路が実際にあり、APIの複雑さに見合う場合に`Cow`を検討する |

- 借用エラーは、所有者と利用期間を確認して解く。無理なライフタイム指定、`'static`化、`Arc<Mutex<_>>`化を初手にしない。境界で所有する設計の方が明瞭なら、小さな値の`clone`も選択肢にする。
- `clone`の意味とコストを型ごとに見る。`Arc::clone(&value)`は参照カウントの共有を明示できるが、深いコピーではない。`Arc`自体は内部データをスレッド安全にしない。
- CLI出力やスナップショットに順序が必要なら明示的にsortするか順序を保証する構造を選ぶ。`HashMap`の反復順序に依存しない。
- パスを内部処理のために文字列化しない。文字列の長さはbytes・Unicode scalar values・表示上の文字のどれが必要かを区別する。整数の縮小変換は失敗を扱う`TryFrom`を基本とし、`as`を入力検証の代わりにしない。

資料: [標準コレクションの選び方](https://doc.rust-lang.org/std/collections/index.html)、
[`Arc`の保証と制限](https://doc.rust-lang.org/std/sync/struct.Arc.html)。

## 不正な状態とエラーを表す

- 実際に取り違えが起こり得るIDや単位にはnewtypeを使う。関連するboolや`Option`の組で無効な状態が生まれるなら、状態を`enum`で表す。単なる値の通過点には不要な型を増やさない。
- 欠けていて正常なら`Option`、失敗の理由が必要なら`Result`を使う。失敗し得る変換は`TryFrom` / `FromStr`、失敗しない変換は`From`にする。
- 検証済みの型は必要に応じてフィールドを非公開にし、生成経路で条件を保つ。`Deserialize`、`Default`、公開フィールドが検証を迂回しないか確認する。境界では未検証の入力型から検証済みの型へ変換する方法も選べる。
- 呼び出し側が分岐する失敗には判別できるエラー型を用意する。アプリケーションの最上位では、既存のエラー集約手段を使ってよい。`anyhow`や`thiserror`を全crateに必須とはしない。原因を保持し、処理・対象が分かる文脈を加え、表示文字列による分岐や秘密情報の混入を避ける。
- 外部入力や通常のI/O失敗を`unwrap` / `expect`で処理しない。テストや、成立根拠が明らかな内部条件では使用できる。`expect`には成立すると考える理由を書く。`.ok()`や既定値への置換で、利用者が知るべき失敗を消さない。

資料: [API Guidelinesの型安全性](https://rust-lang.github.io/api-guidelines/type-safety.html)、
[panicとResultの使い分け](https://doc.rust-lang.org/book/ch09-03-to-panic-or-not-to-panic.html)。

## API と抽象化を選ぶ

- 内部実装は具体的な型と関数から始める。genericsは共通操作を静的に扱う場合、`dyn Trait`は実行時の差し替えや異なる実装の保持が必要な場合、`enum`は候補が閉じている場合に検討する。速度・バイナリサイズ・コンパイル時間の優劣は測定なしに断定しない。
- traitは責務の境界や共通操作を表すために使う。モックのためだけに全関数をtrait化せず、実装が一つという理由だけで有用な境界を削除しない。
- `pub`は利用者に提供する範囲に絞る。内部共有は非公開や`pub(crate)`を検討し、公開フィールド、型、trait boundの変更が利用側へ与える影響を確認する。
- 引数の`impl AsRef<Path>`などは利用側の利便性に効果がある箇所で使う。内部ヘルパーまで一律にgeneric化しない。標準traitの実装も意味が自然に成立するときに加える。
- `unsafe`はsafeな実装では満たせない具体的な理由がある場合に局所化する。必要な条件を記録し、safeな公開APIから条件を破れないようにする。速度向上は代表的な入力で測定する。

資料: [APIの将来の変更に備える設計](https://rust-lang.github.io/api-guidelines/future-proofing.html)、
[API Guidelinesチェックリスト](https://rust-lang.github.io/api-guidelines/checklist.html)。

## 同期・非同期と共有状態を選ぶ

- 短い逐次処理のCLIでは同期処理から検討する。多くのI/Oを待つ、既存基盤がasync、依存APIが要求する場合はasyncを選ぶ。async化だけではCPU処理は速くならない。
- async実行環境のスレッドで長い同期I/OやCPU処理を実行しない。処理量に応じて`spawn_blocking`や専用の実行基盤を検討し、同時実行数も制御する。
- 短く競合が小さい区間をawaitなしで保護するなら、通常のmutexも選択肢になる。awaitをまたぐ必要がある場合はasync mutexを検討し、まずロック範囲を短くできないか確認する。共有状態が不要なら所有権の移動やメッセージ受け渡しを使う。
- spawnした処理の終了、失敗、キャンセルを誰が扱うか決める。リクエスト数に比例して無制限にtaskやqueueを増やさず、必要な上限と待ち方を設ける。
- timeoutやキャンセルで外部への書き込みが取り消されるとは限らない。再試行する処理では重複実行と途中状態を扱い、終了時に完了を待つべき処理を明確にする。

資料: [Tokioの共有状態とmutexの選択](https://tokio.rs/tokio/tutorial/shared-state)。

## 命名・書式・検証

- 関数・変数・moduleは`snake_case`、型・trait・variantは`UpperCamelCase`、定数は`SCREAMING_SNAKE_CASE`。getterは通常`get_`を付けないが、既存APIや取得の意味に合わせる。
- 変換名は、安価な借用ビューに`as_`、借用元から変換結果を作る操作に`to_`、所有権を消費する変換に`into_`を使う。`into_`だから無コストとは扱わない。
- `mut`と変数の有効範囲は必要な箇所に絞る。iteratorとloopはデータの流れが読みやすい方を選ぶ。副作用や複雑な分岐を短いchainへ詰め込まない。自明な処理の説明より、選択理由や維持すべき条件をコメントに残す。
- 書式はrustfmtと既存設定に従う。Clippyの指摘は意味を確認して直し、必要な抑制は理由と範囲を限定する。`pedantic`全体や新しいlint群を依頼と無関係に必須化しない。
- 公開APIは必要に応じて使用例、エラー、panic、unsafeの条件を記述する。変更した動作と失敗経路を既存の検証基盤で確かめる。性能改善を主張する場合はrelease設定・代表的入力・比較条件を示し、検証を行っていない効果を断定しない。

資料: [Rustの命名慣習](https://rust-lang.github.io/api-guidelines/naming.html)、
[APIドキュメントの指針](https://rust-lang.github.io/api-guidelines/documentation.html)。

## 継続運用と検証範囲

通常のCLI・Webバックエンド・ライブラリ開発の共通基準として使う。
組み込み・FFI・暗号・ハードリアルタイム等は、対象分野の追加要件を確認する。
以下のツールをすべての変更で導入・実行する必要はない。

- **依存の更新と安全性。** 導入時の確認だけで終えず、運用する成果物ではRustSec等のアドバイザリを定期的に確認する。既存基盤があれば`cargo audit`等を使い、対象バージョン・到達経路・修正版を確認して対応する。検出なしを安全性の証明とせず、例外には理由と見直し条件を残す。`build.rs`やproc macroも依存の信頼範囲に含める。
- **CIの再現性と対応範囲。** lockfileを使うCIでは`--locked`で意図しない依存解決の変更を検出する。ただしtoolchainや外部ライブラリまで固定されるわけではない。依存更新の検証は別途行う。MSRV・現行stable・対応OS・defaultなしを含むfeature構成から、提供する動作と差分に必要な組合せを選ぶ。`--all-features`一回で全構成を検証したと扱わない。既存の必須チェックは維持する。
- **障害を追える出力。** CLIでは結果と診断の出力先・終了コードを定め、自動処理向け出力へログを混ぜない。サービスでは既存のログ基盤を使い、必要なら`tracing`等でリクエストと非同期処理を関連付ける。エラーの重複記録やトークン・個人情報の出力を避け、調査に必要な識別子と処理の文脈を残す。
- **リスクに応じたテスト。** パーサーや変換では境界値・性質ベースのテスト・fuzzing、unsafeでは対応するコードへのMiri、並行処理では終了・キャンセル・競合の検証を必要に応じて選ぶ。全案件への一括導入やカバレッジ率だけの合否判定はしない。Miriは実行した経路に対する検出手段であり、全入力の健全性を証明しない。追加検証がnightlyを必要としても、製品のMSRVと混同しない。

資料: [RustSec](https://rustsec.org/)、
[CargoのCI設計](https://doc.rust-lang.org/cargo/guide/continuous-integration.html)、
[`--locked`の動作](https://doc.rust-lang.org/cargo/commands/cargo-build.html)、
[`tracing`](https://docs.rs/tracing/latest/tracing/)、
[Miriの用途と限界](https://github.com/rust-lang/miri)。
