# Rust 2024とstable機能の選び方

確認日: 2026-09-21。調査時点のstableはRust 1.98.1。
以下の推奨はnwiizoの最小実装方針に基づく選択基準であり、全機能の採用を要求しない。
新しい機能を使う前に、公式APIの安定化バージョンと対象crateのMSRVを照合する。

## Edition・MSRV・toolchainを分ける

- `edition = "2024"`の最低バージョンは1.85。Editionは互換性の境界であり、
  「2024年の機能だけ」や「以降のstable機能すべて」を意味しない。
- `rust-version`は利用者に示す最低バージョン。ローカルの新しいrustcで通ることを、
  MSRV対応の証拠にしない。workspaceからの継承とCIの実際のtoolchainも確認する。
- 2024ではresolver 3が既定となるが、virtual workspaceでは
  `[workspace] resolver = "3"`を明示する。MSRVを考慮する依存解決は、
  最低バージョンでのビルド検証の代わりにはならない。
- 調査時点の1.98.1は1.98.0のvtable生成不具合を修正している。1.98系を選ぶ場合は
  修正版を使う。これを理由に、依頼外のtoolchainや全プロジェクトを一括更新しない。

根拠: [Edition 2024](https://doc.rust-lang.org/edition-guide/rust-2024/index.html)、
[resolver 3](https://doc.rust-lang.org/edition-guide/rust-2024/cargo-resolver.html)、
[1.98.1の修正](https://blog.rust-lang.org/2026/09/03/Rust-1.98.1/)。

## 借用・一時値・パターン

- 2024の戻り値位置の`impl Trait`は、`use<..>`指定がない場合にスコープ内の
  lifetimeを含むジェネリック引数を捕捉する。意図しない借用の延長には、まず
  `use<..>`による捕捉範囲の明示を検討する。安易な`clone`や`'static`制約を足さない。
  `use<..>`自体は1.82で導入され、Edition 2024専用ではない。
- `if let`が`else`へ進む場合とブロック末尾の式で、一時値の破棄時点が変わる。
  ロック、`RefCell`の借用、独自`Drop`に影響する変更では、コンパイル成功だけで
  判断せず破棄順を確認する。寿命が重要なら変数束縛やブロックで境界を明示する。
- パターンの暗黙の参照束縛と`ref`・`mut`を混ぜる既存コードは移行時に確認する。
  エラー回避のために値を複製せず、参照の型と束縛方法を整理する。

入力を借用しない戻り値であることを表す例（Edition 2024、MSRV 1.85）:

```rust
fn measured_length(input: &str) -> impl Iterator<Item = usize> + use<> {
    [input.len()].into_iter()
}

let mut lengths = {
    let input = String::from("rust");
    measured_length(&input)
};
assert_eq!(lengths.next(), Some(4));
```

型・constジェネリックがある関数へ、この例の`use<>`をそのまま貼らない。
対象toolchainで必要な捕捉引数と、公開APIへの影響を確認する。

根拠: [RPIT捕捉](https://doc.rust-lang.org/edition-guide/rust-2024/rpit-lifetime-capture.html)、
[if letの一時値](https://doc.rust-lang.org/edition-guide/rust-2024/temporary-if-let-scope.html)、
[末尾式の一時値](https://doc.rust-lang.org/edition-guide/rust-2024/temporary-tail-expr-scope.html)、
[パターン](https://doc.rust-lang.org/edition-guide/rust-2024/match-ergonomics.html)。

## unsafe境界は構文修正だけで済ませない

- `unsafe fn`内のunsafe操作にも小さな`unsafe {}`を置き、成立させる条件を近くに
  書く。2024の`unsafe_op_in_unsafe_fn`は既定で警告される。関数全体を囲んで
  警告を消すだけの修正は避ける。
- `unsafe extern`と`#[unsafe(no_mangle)]`等では、FFIシグネチャやシンボルの
  一意性を確認する。属性の囲み直しは安全性の検証にならない。
- `std::env::set_var`・`remove_var`は2024でunsafe。CLIの子プロセス用の設定は
  `Command::env`・`env_remove`で渡し、テストやasync runtime内でプロセス全体を
  書き換えない。単一スレッドである等の条件を立証せずunsafeを追加しない。
- `static mut`への参照は2024で既定deny。用途に応じて不変値、`OnceLock`、
  `LazyLock`、atomic、lockを選ぶ。raw pointerへの置換だけで安全になったと扱わない。

根拠: [unsafe操作](https://doc.rust-lang.org/edition-guide/rust-2024/unsafe-op-in-unsafe-fn.html)、
[extern](https://doc.rust-lang.org/edition-guide/rust-2024/unsafe-extern.html)、
[属性](https://doc.rust-lang.org/edition-guide/rust-2024/unsafe-attributes.html)、
[環境変数](https://doc.rust-lang.org/edition-guide/rust-2024/newly-unsafe-functions.html)、
[static mut](https://doc.rust-lang.org/edition-guide/rust-2024/static-mut-references.html)。

## 最近のstable機能を採用する場面

| 機能・最低バージョン | 採用判断 |
|---|---|
| async closure、`AsyncFn`系: 1.85 | 捕捉した値を借用する非同期コールバックや高階の借用が必要な場面に使う。普通の`async fn`で足りる処理へ導入しない。`Send`やruntimeの要件は別途確認する。 |
| let chains: 1.88 **かつEdition 2024** | 同じ成功経路の入れ子を浅くする。条件が長い場合や失敗理由が異なる場合は、`let else`、`match`、小さな関数を選ぶ。 |
| `std::assert_matches!`: 1.96 | enum等のパターンをテストするとき、失敗値の表示が役立つ。外部入力の検証や通常のエラー処理には使わない。preludeには入っていない。 |
| `core::range`の新しいRange型: 1.96 | 範囲を`Copy`なデータとして保持したいときの候補。`Iterator`ではなく`IntoIterator`を実装する。`0..n`はまだ従来型なので混同しない。既存公開APIの型を機械的に置換しない。 |
| `NumBuffer`と整数`format_into`: 1.98 | 整数整形の割り当てや依存削減が必要な箇所で検討する。通常の表示は`format!`や`write!`の明瞭さを優先し、高速化は測定する。 |

let chainsの例（Edition 2024、MSRV 1.88）:

```rust
fn positive_port(input: Option<&str>) -> Option<u16> {
    if let Some(text) = input
        && let Ok(port) = text.parse::<u16>()
        && port > 0
    {
        Some(port)
    } else {
        None
    }
}
assert_eq!(positive_port(Some("8080")), Some(8080));
assert_eq!(positive_port(Some("0")), None);
assert_eq!(positive_port(Some("invalid")), None);
```

この例は失敗を区別しないAPIに限る。利用者へ原因を返す境界なら`Result`を保つ。

根拠: [1.85](https://blog.rust-lang.org/2025/02/20/Rust-1.85.0/)、
[1.88](https://blog.rust-lang.org/2025/06/26/Rust-1.88.0/)、
[1.96](https://blog.rust-lang.org/2026/05/28/Rust-1.96.0/)、
[NumBuffer](https://doc.rust-lang.org/stable/core/fmt/struct.NumBuffer.html)。

1.98の浮動小数点`algebraic_*`は演算の再配置を許すため、既存の算術演算から
無条件に置換しない。誤差・再現性の要件と測定結果が採用の前提になる。
[1.98の説明](https://blog.rust-lang.org/2026/08/20/Rust-1.98.0/)。

## 移行と検証

1. 既存のEdition・MSRV・feature構成と変更範囲を確認する。移行を依頼されて
   いなければ、対応範囲内の機能を選ぶ。
2. 移行では旧Editionのまま`cargo fix --edition`を実行し、差分を確認してから
   manifestのEditionを変更する。未コミットの別作業を`--allow-dirty`で巻き込まない。
3. 自動修正は旧動作を保存するための変換として読む。`unsafe`の前提、破棄順、
   macro・cfg・公開APIは人手でも確認する。互換性lintの解消だけで移行完了としない。
4. プロジェクト指定のfmt・Clippy・testに加え、MSRVのtoolchainで対象をビルドする。
   cfgの別経路、doctest、サポート対象OSは変更が及ぶ範囲を検証する。
   排他的featureがある場合は`--all-features`だけを合否基準にしない。

1.97以降のCargoには`CARGO_BUILD_WARNINGS=deny`もあるが、既存のClippy設定や
CIゲートを黙って置き換えない。MSRV jobと現行stable jobの役割を分ける。
Edition変更によるrustfmtの差分も、機能変更と区別してレビューする。

根拠: [移行手順](https://doc.rust-lang.org/edition-guide/editions/transitioning-an-existing-project-to-a-new-edition.html)、
[Cargoの警告制御](https://blog.rust-lang.org/2026/07/09/Rust-1.97.0/)。
