# Rust の重複と結合度

構造を変更する実装・修正と、Rust の `review` / `audit` で両CLIを使う。
変更に直接関係する crate とソースを選ぶ。出力のファイル数とモジュール名で
実際の解析範囲を確認し、指摘の採用は依頼された範囲に絞る。
導入済みの0.3.8には、指定パスを無視して workspace 全体を解析する
[不具合](https://github.com/nwiizo/cargo-coupling/issues/86) がある。
この挙動のバイナリでは同じ workspace を一度だけ解析する。
修正版では workspace ルート、crate ルート、ソースパスで範囲を選べる。

## 診断

導入済みのCLIの `--help` で対象バージョンのオプションを確認する。
以下のパスは実際のソースディレクトリと crate ルートに置き換える。

```bash
rtk proxy similarity-rs <source-path> --skip-test --threshold 0.90 --min-lines 10
rtk proxy cargo coupling <crate-root> --exclude-tests --hotspots=10
rtk proxy cargo coupling <crate-root> --exclude-tests --summary
```

最初の2コマンドは独立しているため並行実行できる。重複検出は類似する関数の候補、
結合度解析は変更影響が集まる箇所の候補として使う。`--summary` は全体傾向や
変更前後の比較が必要なときに追加する。類似度や行数の閾値は探索の初期値であり、
プロジェクトに既存の設定があればそれを優先する。

本体を調べるときはテストを除外する。テストそのものが依頼対象なら除外を外す。
マクロ展開、動的な呼び出し、設定条件による実装など、解析外になる経路も考慮する。
`cargo coupling` の未解析範囲を確認するには `--blind-spots` を使う。
Git履歴がない場合は `--no-git` で実行し、変更頻度の情報が欠けることを報告する。

ツールが使えない場合は、エラーと未実行の診断を伝え、読めるコードの確認は続ける。
導入も依頼されていれば既存のパッケージ管理方針に従う。
今回の構造診断だけを理由に別のインストール方法を持ち込まない。

## 結果から判断する

- 類似する関数が同じ責務か、変更理由やエラー時の動作まで共通かを読む。形が似ているだけなら統合しない。
- 候補は関数の組なので、同じ関数を含む組をまとめて判断する。役割別の設定値や異なるイベントの処理は、似た形でも変更理由が違えば残す。型状態付きビルダーの既定値経路などは、新しい抽象化を作る前に既存の状態遷移と生成処理を再利用できるか確かめる。
- 結合が強くても、同じ責務の内部に収まり安定しているなら直ちに問題とはしない。離れたモジュールの内部実装への依存や、変更影響の集中を確認する。
- score、grade、警告数だけを改善目標にしない。trait、facade、newtype、モジュール分割は、確認できた問題を解く場合に選ぶ。
- CLIの出力を根拠に追加する変更は、依頼の範囲と必要な動作を守る。`review` / `audit` だけなら指摘にとどめる。

通常の終了コード0は診断の完了であり、重複なし・結合度に問題なしを意味しない。
`--fail-on-duplicates` や `--check` による品質判定は、リポジトリに基準があるか
依頼されている場合に使う。独自の閾値で突然CIの合否を変えない。

構造を修正したら、同じ対象・オプションで関係する診断を再実行し、修正前後を比較する。
必要なテストも実行して動作を確認する。解析の改善をテストの代わりに扱わず、
確認できた変化と未解析の範囲を報告する。ソースも条件も変わらなければ再実行しない。

動作を保つリファクタリングでは、既存テストに不足があれば変更前に生成結果や失敗経路を固定する。
プロンプトの共通化なら、節の順序、改行、空の節の省略、明示した本文の優先を確認する。
この確認は変更前にも通るテストでよく、不具合修正の失敗再現とは区別する。
検証のlintエラーがマクロ展開から出た場合は生成元と上流の修正版を確認し、
互換更新で解消できるか検証してから、局所的な抑制の必要性を判断する。
